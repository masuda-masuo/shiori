# 事前調査フロー

実装・修正・リファクタリングの前に必ず通す。メモリだけで判断しない。

## ルール

1. **タスクを受け取ったら最初に `shiori_status` で索引の鮮度を確認する。**
   stale なら `shiori_ingest` で更新してから次に進む。

2. **次に `shiori_search` で関連する事前情報を検索する。**
   検索ワードはタスクのドメイン用語 + 類義語 + 英語/日本語両方。
   検索対象は docs / issues / PR discussions / code 全部。

3. **ヒットしたものは `shiori_read_file` / `shiori_read_issue` で読む。**
   「タイトルだけ見て内容を読まない」を禁止する。

4. **設計判断が必要な場合は `architecture-decision-record` スキルを読み込む。**
   過去の ADR と矛盾しないことを確認してから新しい決定を下す。

5. **調査結果を踏まえて方針をユーザーに説明してから実装に入る。**
   「こういう issue/PR があって、現在の設計は〜なので、〜の方針でやります」と一言はさんでからコードを書き始める。

6. **実装後は新しく得た知見を docs/ か issue/PR に残す。**
   以下のいずれか:
   - ADR を書く（`architecture-decision-record` スキルを使用）
   - Issue にコメントする
   - PR description に決定事項を書く
   他のエージェントが後で `shiori_search` で発見できるようにする。

## 例外

- 単純なバグ修正（原因が特定済み、直すだけ）は skip してよい
- 明らかに自明なリネーム・タイポ修正も skip してよい
- 上記以外は必ず通す
