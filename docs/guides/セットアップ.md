# セットアップ

## 前提

- Docker / Docker Compose
- （非公開リポジトリを索引する場合）リポジトリ読み取り権限のある GitHub トークン

## 手順

```bash
git clone https://github.com/<your-username>/shiori.git  # フォークまたはクローン元に読み替え
cd shiori
cp .env.example .env
# .env を編集:
#   SHIORI_REPOS=owner/name      （カンマ区切りで複数可）
#   GITHUB_TOKEN=ghp_xxx         （公開リポジトリのみなら空でも可）

# DB と MCP サーバーを起動（初回はイメージビルド）
docker compose up -d --build

# 索引を作成（初回は埋め込みモデルのダウンロードを含むため時間がかかる）
# private リポジトリを索引する場合は、事前に .env で認証の設定が必要
# （方式は3つ。詳細は下記「認証方式の選び方」を参照:
#   1. GitHub App 秘密鍵ファイル方式（GITHUB_APP_ID / GITHUB_APP_PRIVATE_KEY_PATH を
#      docker-compose.override.yml の secrets で読み取り専用マウント）
#   2. TokenCommand の token-file 橋渡し方式（GITHUB_TOKEN_COMMAND=cat /run/shiori/github-token。
#      WSL/Linux の常設運用で実際に使われている方式）
#   3. PAT なら GITHUB_TOKEN）
# 注意: --build を忘れるとコード修正が反映されない（docker compose run は自動再ビルドしないため）
docker compose run --build --rm ingest

```

`ingest` サービスは `command` を内蔵しているため引数不要で、`app` と同じ認証設定を持つが、使い捨てジョブとして分離されている。

**認証方式の選び方（issue #188）:** `build_token_provider()` の優先順位は
**App > TokenCommand > PAT(static) > mcp_token > anonymous**。実運用で使うのは次の3方式。

1. **GitHub App 秘密鍵ファイル方式** — `GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY_PATH` を
   `docker-compose.override.yml` の `secrets` で読み取り専用マウントする。秘密鍵そのものが
   コンテナに入る。masuda-masuo/dev-infra#4 / #5 の GCP VM で実運用中。
2. **TokenCommand の token-file 橋渡し方式** — **ホスト側**で `mcp-token` が OS keystore
   から App 認証情報を読んで短命トークンを mint し、`runtime/github-token` に書き続ける
   （`scripts/refresh-token.{sh,bat}`）。コンテナは `./runtime:/run/shiori:ro` マウント越しに
   `GITHUB_TOKEN_COMMAND=cat /run/shiori/github-token` で読むだけで、**秘密鍵はコンテナに
   渡らない**。WSL の常設運用（後述の systemd 方式）で実際に使われているのはこちら。
3. **McpTokenProvider（プロセス内 mint）** — `GITHUB_TOKEN_COMMAND` 等を設定しなかった場合の
   フォールバック。mcp-token バイナリをプロセス内で解決して自ら mint する、**ネイティブ実行
   専用**の方式（後述の「コンテナを使わずローカルの Python で stdio 接続したい場合」等）。
   コンテナ内では keystore の D-Bus session bus がバスオーナー UID しか受け付けないため mint
   に失敗し、警告ログ1行のまま匿名へ静かにフォールバックする。

「credential の消費者がコンテナ内なら、資格情報を消費者側に運ぶ」というルール（issue #188）は
方式1（鍵を運ぶ）・方式2（短命トークンを運ぶ）の両方が満たしており、どちらもコンテナで使える。
方式3だけがこのルールを満たせず、コンテナ内では成立しない。方式2は秘密鍵そのものがコンテナに
入らない利点がある。

`shiori_status` の `token_provider` フィールドで実効 provider（`app` /
`static` / `token_command` / `mcp_token` / `anonymous` / `error`）を確認できる。
`error` は provider 構築自体の失敗（例: App 設定の一部欠け）を示し、例外
メッセージが `warnings` に載る（issue #193）。

### Windows での手動運用（scripts/）

日常運用は Windows では `scripts/*.bat` に集約されている:

| スクリプト | 役割 |
| --- | --- |
| `scripts/run-shiori` | トークン更新ループを起動し、app コンテナを build + 起動 |
| `scripts/stop-shiori` | トークン更新ループ・旧ホスト serve・app コンテナを停止 |
| `scripts/update` | `git pull` + イメージ再ビルド + app 再起動 |
| `scripts/ingest` | ワンショット同期（`--rebuild` などの引数はそのまま渡る） |
| `scripts/refresh-token` | 短命トークンを `runtime/github-token` に発行（run-shiori が内部で利用） |

2 回目以降の `ingest` は差分同期（docs はファイルハッシュ、issue/PR は `updated_at` カーソル）なので速い。

### Linux/WSL での常設運用（systemd user unit）

Linux/WSL の常設運用は systemd user unit が正。`git clone` 後に一度、`scripts/install-systemd.sh` を実行すればよい:

```bash
./scripts/install-systemd.sh
```

このスクリプトが `scripts/` 配下の3つのユニットファイルをテンプレート展開（`@SHIORI_DIR@` をクローン先の絶対パスに置換）して `~/.config/systemd/user/` に配置し、`daemon-reload` の後に `shiori.service` と `shiori-refresh.timer` を `enable --now` する。実体は次のファイルで、`install-systemd.sh` が置換して配置するもの以外に手を加える必要はない:

| ファイル | 配置後のユニット | 役割 |
| --- | --- | --- |
| `scripts/shiori.service` | `shiori.service` | `ExecStartPre=-scripts/refresh-token.sh` の後に `docker compose up -d app` を実行（Type=oneshot / RemainAfterExit=yes）。停止は `docker compose stop app`、再起動は `docker compose restart app`。 |
| `scripts/shiori-refresh.service` | `shiori-refresh.service` | `scripts/refresh-token.sh` を1回実行する oneshot（timer から呼ばれる）。 |
| `scripts/shiori-refresh.timer` | `shiori-refresh.timer` | 5分間隔（`OnUnitActiveSec=300`）で `shiori-refresh.service` を起動し、`runtime/github-token` を更新し続ける（`BindsTo=shiori.service`）。 |

**落とし穴:** `shiori.service` は `docker compose up -d app` するだけで
**`--build` しない**。コードを更新したら明示的に再ビルドしてから再起動すること:

```bash
docker compose build app
systemctl --user restart shiori.service
```

**トークン更新タイマーは load-bearing（入れ忘れると1時間後に401）:** `TokenCommandProvider` が読んだトークンを
キャッシュする最長時間は50分、App installation token の寿命は60分。トークン
ファイルは常に10分未満の鮮度を保つ必要があるため、`shiori-refresh.timer` による5分（300秒）間隔の更新が欠かせない。
`install-systemd.sh` を実行せずに `shiori.service` だけを手で `enable` した場合や、`shiori-refresh.timer` を
無効化・間隔延長した場合は、起動直後は動いているように見えても約1時間後にトークンが失効し、
private リポジトリの同期が 401 で止まる（`shiori_status` の `token_provider` で実効 provider を確認できる）。

## 索引の更新（3 経路）

| 経路 | 用途 |
| --- | --- |
| `SHIORI_SYNC_INTERVAL_SECONDS` | serve プロセス内のバックグラウンド自動同期。ポーリング間隔を設定（例: 10 秒）。 |
| CLI `python -m shiori ingest` | 初回構築・cron 等のスケジュール実行（`docker compose run --build --rm ingest`） |

## 埋め込みモデルの変更

埋め込みモデルを変更した場合は全件再索引する:

```bash
docker compose run --build --rm ingest -- --rebuild
```


## MCP クライアントからの接続

MCP サーバーは streamable HTTP で `http://localhost:8765/mcp` に公開される。

例: Claude Code

```bash
claude mcp add --transport http shiori http://localhost:8765/mcp
```

コンテナを使わずローカルの Python で stdio 接続したい場合:

```bash
pip install -e .
DATABASE_URL=postgresql://shiori:shiori@localhost:5432/shiori \
  python -m shiori serve --transport stdio
```

（compose の `db` は 127.0.0.1:5432 に公開済み。Windows ホストの場合は
`SHIORI_DATA_DIR` にクローン先ディレクトリの指定が必要）

## 提供される MCP ツール

| ツール | 用途 |
| --- | --- |
| `shiori_search` | 意味＋キーワードのハイブリッド検索（統合入口）。まずこれを使う |
| `shiori_keyword_search` | 固有名詞・API 名・エラーコード等の厳密一致（補助ツール） |
| `shiori_list_tree` | 索引済みドキュメント＋コードファイルのパス一覧 |
| `shiori_read_file` | ファイル全文（または行範囲）の取得 |
| `shiori_read_issue` | issue / PR スレッド全体の取得 |
| `shiori_pr_changes` | PR の変更ファイルマップ（メタデータ）。head_sha と変更ファイル一覧 |
| `shiori_status` | 索引の鮮度と健全性の確認 |

## トラブルシューティング

- **`EMBEDDING_DIM=... but model produces ...`:** モデルと次元の組み合わせが不一致。`.env` の `EMBEDDING_DIM` をモデルの次元に合わせ、`ingest --rebuild` を実行。
- **検索が 0 件:** `ingest` が完了しているか、`SHIORI_REPOS` が正しいかを確認。
- **コード修正が反映されない:** `docker compose run` はイメージを自動再ビルドしない。`--build` フラグをつけるか、事前に `docker compose build` を実行する（#17 のキャッシュ最適化により再ビルドは数秒）。`docker compose up -d app` の場合も同様に `--build` をつける。
- **`git clone failed ... could not read Username`:** private リポジトリには `GITHUB_TOKEN` が必要。
- **API レート制限:** `GITHUB_TOKEN` を設定すると上限が大きく緩和される。
