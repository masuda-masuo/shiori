> **ステータス: 将来構想（未実装 / future direction, not scheduled）。** 本書は「issue は Jira、設計書は Confluence」のように複数プロダクトに分散したナレッジを、shiori の単一索引で横断検索できるようにするための抽象化を提案する。
>
> **当面のスタンス: 実装しない。拡張性だけ確保する。** これは将来やるかもしれない構想であり、現時点で着手予定はない。本書の役割は「いざやるとなったときに困らないよう、いま扉を閉じないための判断基準」を残すことにある。したがって当面 shiori に対してすべきことは、下記「当面のガードレール」を意識するだけでよい。以降のスキーマ変更・コネクタ抽象・フェーズ計画は、**将来着手する場合の設計図**であって、いま実装する TODO ではない。着手時には `00-基本設計.md` §3〜§5 と `13-プロダクト定義とユースケース.md` の一文定義を更新する（§「基本設計への反映」参照）。

## 当面のガードレール（実装せずに拡張性だけ保つ）

いま新しいコードを書くとき、次を避ければマルチソース化の扉は閉じない。追加コストはほぼゼロ:

- **`source_type` を「プロダクト」ではなく「ナレッジの種類」として扱う。** `issue` は「GitHub の issue」ではなく「issue というナレッジの種類」。コードやドキュメント・description で「GitHub issue」と密結合に語り切らない。
- **`chunk_key` を不透明キーとして保つ。** 形式に依存した解析（`split(":")` で GitHub 前提の位置を仮定する等）を新たに足さない。
- **GitHub 固有の想定を検索・スキーマの中核に新規に埋め込まない。** 例えば `issue_no` が必ず整数である前提の分岐を検索層に増やさない。既存分はそのままでよい（`source='github'` デフォルトで生きる）。
- **判断に迷ったら「これは GitHub だからか、issue だからか」を問う。** 後者に属する仕様は将来他ソースにも効く。前者はコネクタ内に閉じ込める。

逆に、この構想のために**いま前もって作り込むべきものは無い**。`source` 列もコネクタ抽象も、必要になった時点で後付けできる（既存行は無改修で移行できる設計 — §「設計」参照）。

## 目的

現状の shiori は GitHub 単体のナレッジ（docs / issue・PR / code）を索引・検索する。しかし実務では、同じプロジェクトの知識が複数プロダクトに分散していることが多い:

- **issue / チケット** → Jira
- **設計書 / 仕様** → Confluence、Notion、Google Drive
- **コード / PR** → GitHub / GitLab

「issue」「ドキュメント」という**ナレッジの種類**を、それを保持する**プロダクト（＝ソース）**から切り離して抽象化すれば、複数ソースから集めたものを単一の索引に載せて横断検索できる。これは shiori の核となる価値（`13` §1「横断検索と関連付け」）を、GitHub の境界を越えて拡張するものであり、本 MCP の独自性を一段強める。

## 背景 — なぜ shiori はこの拡張に適しているか

大規模な書き換えは不要である。マルチソース横断検索に必要な「難しい部分」は、既にソース非依存に作られている:

1. **索引・検索層が既にソース非依存。** `chunks` は単一テーブル（`04`）で、`search.py` は `source_type` / `repo` / `state` などの汎用列でフィルタするだけ。ベクトル（pgvector）＋全文（pgroonga）＋RRF 融合＋クロスリンガル埋め込みという「横断検索の核」は、チャンクの出所を問わない。
2. **pointer-then-fetch の思想が既にマルチソース向き。** shiori は未確定コンテンツの全文を保持せず、「座標＋URL」だけを返して全文取得を GitHub MCP に委譲する（`00`「目的とスコープ」/ `13` §3）。この委譲先を Jira MCP / Confluence MCP に置き換えれば、同じ思想がそのまま各プロダクトに一般化する。
3. **非 GitHub ソースの先例が既に設計済み。** `08-ファイルシステム取り込み.md`（fs ソース）は、`repo="fs:{name}"` というプレフィックス規約で非 GitHub ソースを 1 テーブルに同居させ、チャンク・埋め込み・スキーマ・検索を無改修で流用する方式を確立している。本書はこの先例を一般化する。

したがって本課題の本質は「4000 行の書き換え」ではなく、**(a) ソース次元の導入、(b) コネクタ抽象の導入、(c) 座標モデルの一般化**の 3 点に集約される。

## 中核となる概念モデル — `source` と `source_type` の分離

現状の `source_type`（`doc` / `issue` / `pr_review` / `code`）は、直交する 2 つの概念を暗黙に混在させている:

- **どのプロダクトから来たか**（暗黙に常に GitHub）
- **どんな種類のナレッジか**（doc / issue / code …）

マルチソース化ではこれを 2 次元に分離する:

| 次元 | 意味 | 値の例 |
|---|---|---|
| **`source`（コネクタ）** | ナレッジが**どこから**来たか | `github` / `jira` / `confluence` / `fs` / `gitlab` |
| **`source_type`（種類）** | **どんな**ナレッジか | `doc` / `issue` / `code` / `pr_review` |

これでユーザーの直感が素直にモデル化される:

| ナレッジ | source | source_type |
|---|---|---|
| GitHub の issue | `github` | `issue` |
| Jira のチケット | `jira` | `issue` |
| main 上の Markdown | `github` | `doc` |
| Confluence のページ | `confluence` | `doc` |
| ローカルのメモ（`08`） | `fs` | `doc` |

`shiori_search(source_type="issue")` は GitHub issue と Jira チケットを**同じランキングに載せる**。これがマルチソース横断検索の実体であり、独自性の源泉である。`source` フィルタで「Jira だけ」「GitHub＋Jira」といった絞り込みもできる。

## 設計

### 1. スキーマ変更（`04` の拡張）

`chunks`（および `issue_items`）に `source` 列を追加する。既存 GitHub 行のデフォルトは `'github'`。

```sql
ALTER TABLE chunks ADD COLUMN source TEXT NOT NULL DEFAULT 'github';
CREATE INDEX chunks_source_idx ON chunks (source);
-- source_type の CHECK は種類のみに保つ（プロダクト値は source 列へ）
```

**座標モデルの一般化（最重要）。** 現状の自然キー列は GitHub 形状に固定されている: `repo`(owner/name)、`issue_no`(INTEGER)、`comment_id`(BIGINT)。Jira のキーは `PROJ-123`（文字列）、Confluence はページ ID ＋スペースであり、整数の `issue_no` には収まらない。

- **`chunk_key`（TEXT）は既にソース非依存の不透明キー**（`doc:repo:path` 等）。各コネクタが自前のスキーム（例 `jira:PROJ-123:comment:456`）を定義すればよく、ここは変更不要。
- **`repo` 列は「スコープキー」として一般化する。** fs の先例（`repo="fs:notes"`）に倣い、`jira:PROJ` / `confluence:SPACE` のようにコネクタ固有のワークスペース識別子を格納する。GitHub は従来どおり `owner/name`（`/` を含むため衝突しない）。列名は互換のため `repo` を維持し、ドキュメント上「スコープキー」と定義し直す。
- **`native_id TEXT`（新規）を正準座標とする。** `issue_no`(INTEGER) は GitHub 専用の射影として残し、ソース中立の識別子は `native_id`（例 `PROJ-123`、`#42`、Confluence ページ ID）に持たせる。検索結果のポインタは `{source, scope(repo), native_id, url}` を返す。

移行は `_run_alter_statements`（`db.py`）に冪等な `ADD COLUMN IF NOT EXISTS` を追加する既存パターンを踏襲する。既存 GitHub デプロイは `source='github'` / `native_id=NULL`（従来の `issue_no` を使用）で無改修動作する。

### 2. コネクタ抽象（`SourceConnector` プロトコル）

現状 `ingest.py` は `sync_docs` / `sync_issues` / `sync_code`（すべて `github_sync.py`）を直接呼ぶ。これをプロトコル越しの登録制に変える。

```python
class SourceConnector(Protocol):
    source: str                       # 'github' | 'jira' | 'confluence' | ...

    def scopes(self, settings) -> list[str]:
        """同期対象のスコープ（repo / project / space）を返す。"""

    def sync(self, settings, conn, embedder, scope, *, buffer=None) -> SyncResult:
        """1 スコープを差分同期する。正規化チャンクを索引し、
        read 用の生データと関係エッジを保存する。件数を返す。"""
```

- `github_sync` を `GitHubConnector` として本プロトコルに適合させる（第一実装）。挙動は不変。
- `fs_sync`（`08`）を `FsConnector` として実装（第二実装。設計は既存）。
- `ingest.py` のフェーズ列挙を `for connector in registered_connectors: for scope in connector.scopes(...): connector.sync(...)` に置き換える。advisory lock・`ChunkBuffer`・`record_sync_run` の枠組みは不変。
- コネクタ登録は設定駆動（例 `SHIORI_SOURCES=github,jira`）。未設定時は `github` のみ＝現状と完全互換。

各コネクタが吸収する差分: 認証、API のページネーションとレート制限、差分同期カーソル（`sync_state.cursor` はソースごとに意味が異なる — GitHub は `updated_at`、Confluence は version、Jira は JQL の updated）、正規化（各プロダクトのフィールド → 共通チャンク列）。

### 3. 検索層（`05` の拡張）

`search.py` の `_filter_sql` に `source` を追加するのみ（`source_type` と同じ 1 行の等値フィルタ）。RRF 融合・ランキングロジック（`_rank_candidates`）は無改修。`SearchHit` に `source` / `native_id` を追加し、ポインタとして返す。

ランキングの `source`-aware tie-break（現状 doc/code=一次、issue/pr=二次）は `source_type` ベースのまま維持でき、プロダクト非依存。将来「同じ `source_type=issue` でも Jira と GitHub で重みを変えたい」場合の拡張余地は残すが、v1 相当では等価に扱う。

### 4. 閲覧・関係層（層②③）はコネクタ能力として提供

層①（検索）は**ソース中立で普遍**だが、層②③（閲覧・関係）は本質的にプロダクト固有である（PR diff に Jira の対応物はない）。設計原則:

- **検索ポインタは `source` を含む**ため、閲覧ツールはそれでディスパッチできる。`shiori_read_issue(number, repo?)` は `source` を見て各コネクタの reader に委譲する形へ一般化する（GitHub=スレッド API、Jira=issue＋コメント）。
- **プロダクト固有ツール**（`shiori_pr_diff` 等）は、そのソースを持つコネクタが能力を提供するときだけ有効。コネクタが未対応の操作はエラーで明示する。
- **未確定・ライブコンテンツの全文取得は各プロダクトの MCP に委譲する。** GitHub MCP への委譲（`13` 非目標表）を、Jira MCP / Confluence MCP へ一般化する。shiori は検索可能にするためにテキストを索引するが、全文の正となる取得は各プロダクト MCP に任せる — pointer-then-fetch の思想がそのままスケールする。

## スコープ上の判断 — これは意図的な定義拡張である

`00`・`13` は「GitHub の再発明を避ける」「GitHub MCP に委譲する」を繰り返し強調しており、一文定義も「GitHub リポジトリに散在するプロジェクトナレッジ」に限定している。マルチソース化はこの**ミッションの意図的な拡張**であり、単なる機能追加ではない。着手前に次を意識的に決める必要がある:

- **拡張後の一文定義**: 「GitHub リポジトリに散在する」→「プロジェクトのナレッジソース（GitHub・Jira・Confluence 等）に散在する」。
- **同じ原則がソース単位でスケールする**こと: shiori は各ソースを横断検索用に索引しポインタを返す／各プロダクトの MCP が書き込み・ライブ取得・固有操作を担う。「再発明を避ける」原則は破られず、委譲先が増えるだけである。
- **コスト**: コネクタごとに API・認証・レート制限・差分同期・正規化の保守が増える。価値（横断検索の対象拡大）とのトレードオフを、対象プロダクトを絞って（まず 1 つ）検証する。

## 実装フェーズ

段階的に、各フェーズ単体で既存 GitHub デプロイに無影響（`source='github'` デフォルト）となるよう分割する。

- **フェーズ 0（本書）**: `source` / `source_type` の分離と、定義拡張の意思決定。
- **フェーズ 1（抽象化のみ、新ソースなし）**: `source` 列追加、`SourceConnector` プロトコル導入、`github_sync` をプロトコル適合、検索層に `source` フィルタ追加。新コネクタは足さない。これで「横断検索の器」が整い、挙動は不変。
- **フェーズ 2（座標一般化）**: `native_id` 追加、閲覧ツール（`read_issue` 等）を `source` ディスパッチに一般化。`fs` コネクタ（`08`）を第二実装として投入し抽象の妥当性を実証。
- **フェーズ 3（最初の外部プロダクト）**: Jira か Confluence のどちらか一方をコネクタ実装。ライブ全文取得は当該プロダクト MCP に委譲。実データで横断検索の精度と運用コストを計測。

フェーズ 1・2 は外部依存ゼロ（fs はローカル）で価値の器を先に作れるため、フェーズ 3 の投資判断を計測に基づいて行える。

## 検討事項 / 未決

- **最初の外部プロダクトの選定**: Jira（issue 側、`source_type=issue` の横断が最も価値が見えやすい）と Confluence（doc 側）のどちらを先に実証するか。ユーザーの利用実態で決める。
- **差分同期カーソルの抽象**: `sync_state.cursor` はソースごとに意味が異なる（`updated_at` / version / JQL）。コネクタ内に閉じるか、汎用スキーマを設けるか。
- **関係（層③）の横断**: GitHub issue → Jira チケットのような**ソース間リンク**をたどれるか。`shiori_issue_links` の相互参照抽出をソース横断に広げる余地（例: PR 本文中の `PROJ-123` を Jira ポインタとして解決）。将来課題。
- **埋め込み・pgroonga の言語対応**: 新ソースのテキストも既存の多言語モデル＋TokenMecab で無改修に索引できる（クロスリンガルの利点はソースを問わない）。
- **認証の抽象**: 現状 `build_token_provider` は GitHub 専用。コネクタごとの認証（Jira API トークン、Confluence PAT 等）を `config` にどう収めるか。
