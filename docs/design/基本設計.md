# 基本設計

## 1. 目的とスコープ

shiori は、GitHub リポジトリの知識（Markdown ドキュメント＋ issue/PR の議論）を、AI エージェントが効率的に参照できるようにするローカルな MCP サーバーである。

- **解決する課題:** 汎用 MCP 経由ではファイル全文を読むしかなく、トークン消費が大きくコンテキストを圧迫する。
- **基本方針:** 「検索してポインタを返す → 必要分だけ取得する」という 2 段構えにより、コンテキストに届く情報を関連断片に絞る。
- **対象:** 公開・非公開の両方のリポジトリ。日本語・英語が混在するコンテンツ（ファイル単位では言語は統一されている前提）。

## 2. 設計原則

- ローカル完結・プライベート（非公開リポジトリを扱うため、データを外部に出さない）
- 検索優先・取得は後（pointer-then-fetch）
- ハイブリッド検索（意味検索＋キーワード検索）
- 関心事の統合（ベクトル・全文・メタデータを単一 DB に）
- コモディティ層は再利用し、検索／オーケストレーション層を自作（学習目的も兼ねる）

## 3. 全体構成

処理の流れ: **同期 → チャンク分割 → 埋め込み → 索引 → 検索 → MCP 公開**。

- データ源は 2 系統: docs（git 経由）と issue/PR（API 経由）。
- 実行は 2 コンテナ: DB（Postgres）と MCP サーバー（compose で分離）。

## 5. 主要な設計判断（決定ログ）

- ストアは **Postgres に集約**（pgvector + pgroonga/pg_bigm）。TiDB はローカル必須要件のため不採用。
- 専用ベクトル DB（Qdrant 等）ではなく Postgres を選択。理由: 規模が小さく、ベクトル＋メタデータ＋日本語キーワードを 1 システムで完結させたい。日本語全文は pgroonga/pg_bigm で実績ベース。
- コンテナは **db/app 分離**（同居しない）。理由: イテレーション時に DB を巻き込まない、コンテナの 1 プロセス原則（PID1）、公式系イメージの活用。
- 日本語キーワード検索には**形態素解析が必須**（英語前提のトークナイザでは日本語が引けない）。
