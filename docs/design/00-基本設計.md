# 基本設計

## 1. 目的とスコープ

shiori は、GitHub リポジトリに散在するプロジェクトナレッジ（ドキュメント・ソースコード・issue/PR の議論）を、AI エージェントが横断して検索し、関連付けてたどれるようにするローカルな**プロジェクトナレッジ検索 MCP** サーバーである。当初は RAG 基盤として構想されたが、回答生成は担わず検索とナレッジナビゲーションに徹する現在の定義に改めた（プロダクト定義・ユースケースの詳細は `詳細設計/13`）。

- **解決する課題:** 一つの問いに答える知識が docs・code・issue/PR に分散しており、特に issue/PR に埋もれた経緯・判断にはエージェントが実用的に到達できない（GitHub 標準検索は意味検索でもクロスリンガルでもない）。汎用 MCP 経由の全文読み込みはトークン消費・コンテキスト汚染も大きい。
- **基本方針:** 3 種のナレッジを単一索引で横断検索・関連付けし、「検索してポインタを返す → 必要分だけ取得する」という 2 段構えにより、コンテキストに届く情報を関連断片に絞る（低トークンは存在理由ではなく設計原則 — `詳細設計/13`）。
- **対象:** 公開・非公開の両方のリポジトリ。日本語・英語が混在するコンテンツ（ファイル単位では言語は統一されている前提）。

## 2. 設計原則

- ローカル完結・プライベート（非公開リポジトリを扱うため、データを外部に出さない）
- 検索優先・取得は後（pointer-then-fetch）
- ハイブリッド検索（意味検索＋キーワード検索）
- 関心事の統合（ベクトル・全文・メタデータを単一 DB に）
- コモディティ層は再利用し、検索／オーケストレーション層を自作（学習目的も兼ねる）

## 3. 全体構成

処理の流れ: **同期 → チャンク分割 → 埋め込み → 索引 → 検索 → MCP 公開**。

- データ源は 2 系統: docs（git 経由）と issue/PR（API 経由）。
- 実行は 2 コンテナ: DB（Postgres）と MCP サーバー（compose で分離）。

## 5. 主要な設計判断（決定ログ）

- GitHub 認証は TokenProvider 抽象。優先順位は App > TokenCommand（GITHUB_TOKEN_COMMAND）> PAT >
  anonymous。compose デプロイでは GitHub App 秘密鍵ファイル方式（鍵を app / ingest に
  渡す）と token-file 橋渡し方式（鍵は渡さず短命トークンのみファイル経由で渡す）
  のどちらかを使う（`詳細設計/09`）。方式の選択規則と、両方式の制約を外す到達点
  （on-demand mint socket）は `詳細設計/15`。
- ストアは **Postgres に集約**（pgvector + pgroonga）。TiDB はローカル必須要件のため不採用。
- 専用ベクトル DB（Qdrant 等）ではなく Postgres を選択。理由: 規模が小さく、ベクトル＋メタデータ＋日本語キーワードを 1 システムで完結させたい。日本語全文は pgroonga で実績ベース。
- コンテナは **db/app 分離**（同居しない）。理由: イテレーション時に DB を巻き込まない、コンテナの 1 プロセス原則（PID1）、公式系イメージの活用。
- 日本語キーワード検索には**日本語を正しく索引できるトークナイザが必須**。pgroonga の TokenMecab（形態素解析）を第一候補とし、無い環境では TokenBigram に自動フォールバック（`詳細設計/04`）。

### v1 実装時の決定（2026-06）

- 全文拡張は **pgroonga を採用**（pg_bigm 不採用）。チャンクは `source_type` 列で **1 テーブル統合**（`詳細設計/04`）。
- issue スレッドは**生のまま索引**（取り込み時の要約生成は不採用。`詳細設計/02`）。
- **リランクモデルは不採用**。ハイブリッド融合は **RRF（k=60）** のみ。`shiori_search` が統合入口で内部ハイブリッドを行い、`shiori_keyword_search` は厳密一致用に分離して維持（`詳細設計/05`・`06`、issue #40）。
- 同期は**オンデマンドの ingest コマンド**（一回限りのコンテナ実行）。差分同期は docs=コンテンツハッシュ、issue/PR=`updated_at` カーソル。bot コメントは索引から除外（`詳細設計/01`・`07`）。
- 埋め込みの既定は **multilingual-e5-small（384 次元）**。環境変数で差し替え可、変更時は再索引（`詳細設計/03`）。
- MCP は **streamable HTTP（:8765）** を既定トランスポートとする（`詳細設計/07`）。
- 検索ランキングは**関連度主に固定**。日付並べ替えは一次（doc/code）では提供せず、二次（issue/PR）でも `state` / `updated_at` を tie-break に留める。「最近クローズ / 変更」等の日付トリアージは **GitHub MCP に委譲**し再実装しない（README「目的とスコープ」= GitHub の再発明を避ける）。`sort_by` の関連度置換（issue #41 / PR #67）は見直し（`詳細設計/05`）。

## 6. 未決事項（サマリ）

v1 実装で当初の未決 4 点（全文拡張・issue 要約・リランク・同期方式）は解消した。残る検討事項:

- merged PR の判定取得と「結論」志向のブースト（`詳細設計/01`・`05`）
- 実データでの検索精度計測と、埋め込みモデルのグレードアップ判断（`詳細設計/03`）
- リランクモデルの再評価 — RRF の実測精度が不足した場合（`詳細設計/05`）
- fs（ローカルディレクトリ）ソースの取り込み — 詳細設計は `08` にあるが v1 未実装（`08`）
