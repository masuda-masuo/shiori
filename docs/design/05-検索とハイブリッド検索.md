# 詳細設計: 検索とハイブリッド検索

## 目的

意味検索とキーワード検索を組み合わせ、関連度の高い結果を返す。返すのは「ポインタ＋スニペット」で全文ではない。

## ハイブリッド検索

- **意味検索（pgvector）:** 言い換え・概念に強い。クロスリンガルもここで担う。
- **キーワード検索（pgroonga/pg_bigm）:** 固有名詞・API 名・エラーコード・識別子の完全一致に強い。日本語は形態素解析が前提。
- **融合:** 両者のランキングを RRF などで統合し、再ランクする。
- **フィルタ:** `source_type` / `language` / `state` / 日付 等で `WHERE` 句による絞り込み。

## 鮮度の扱い

- 古いクローズ済みの issue は現在の挙動と食い違うことがある。`state` と日付を前面に出し、必要に応じて新しいものを重み付け。

## 返却形式（pointer-then-fetch）

- 検索ツールは「パス / 見出しアンカー / issue 番号 ＋ スニペット ＋ メタデータ」を返す。
- 全文はエージェントが必要と判断したときに read 系ツールで取得する。

## ソートとランキング方針（issue #41 を見直し）

検索ランキングは関連度主に固定する。PR #67 で全 `source_type` に一律で入れた `sort_by` の関連度置換ソートは、下記ユースケース分析の結果、一意に必要とする場面が無いため見直す。

### ソース別の方針

- **一次（doc / code, 確定・現在）:** 関連度（RRF）のみで並べる。日付ソートは提供しない。確定情報は recency に「正しさの勾配」を持たず、日付で並べ替えると唯一有用な信号（関連度）を無価値な信号に置換してしまうため。
- **二次（issue / pr_review, 過去〜未確定が混在）:** 関連度で候補プールを作り、`state` / `updated_at` を tie-break（二次信号）として重ねる複合ランキング。純粋な日付置換ソートは提供しない。

### 二次ソースを引く動機と自然な並び

| 動機 | 例 | 自然な並び | 採るもの |
|---|---|---|---|
| 判断の根拠（なぜ） | この設計はどこで決まったか | 関連度＋結論 | 関連度主＋結論（merged PR / クローズ時コメント）ブースト |
| 既出 / 却下案の確認 | 既に提案・却下された案はあるか | 関連度＋`state` | 関連度主、`state` 考慮（却下案は古くても重要） |
| 最新の考え | この件の現在の結論 | 関連の中で最新 | 原則 doc（確定）を読む。issue 側は関連度＋`updated_at` tie-break |
| 最近の変更 / トリアージ | 最近クローズした issue 一覧 | 日付（メタ列挙） | shiori では持たない → GitHub MCP に委譲 |
| うろ覚え探索 | 埋め込みモデルの議論はどこか | 関連度 | 関連度のみ |
| 時系列監査 | 判断の変遷を追う | トピック絞り→日付 | 関連度で絞る＋`read_issue` の時系列出力 |

### 決定

- 純日付ソート（`sort_by=updated_at/created_at` の関連度置換）を一意に必要とするユースケースは無い。日付ニーズは全て (1) 関連度内の tie-break か (2) メタ列挙（GitHub MCP 委譲）のどちらかに解消される。
- 入口 `shiori_search` は関連度主に固定。二次ソースの `state` / `updated_at` は tie-break までに留める。`keyword_search` も同様。
- 「最近クローズ / 変更」のトリアージ（上表「最近の変更」）は GitHub MCP / `gh issue list` に委譲し、shiori で再実装しない。README「目的とスコープ」の「全部を抱えると GitHub の再発明」を避ける方針に従う。
- 混合（doc ＋ issue ＋ PR）検索の価値は「場所が未知の discovery」に限定。確定情報の問いは一次ソースを主に答える。

### 実装上の含意

- 二次ソースの複合 tie-break は `sorted(...)[:k]`（top-k 切り詰め）の **前**、候補プール段で行う。現状の truncate-then-sort はプール外の候補を取りこぼすため不可。
- PR #67 の `sort_by` 純置換は撤去、または二次ソースの tie-break 指定に限定する（実装は別 PR）。

## 検討事項 / 未決

- リランクモデル（ローカル・多言語）の採否と選定。
- 「結論」志向の検索: クローズ時コメントや紐づく merged PR のブースト → 上記「二次ソースのランキング」の一部として実装する（位置づけ確定）。
- top-k の決め方（固定 K vs 関連度ギャップでの足切り）。複合 tie-break を入れる場合は候補プール段で行う点に注意。
- （解決）日付ソートの採否 → 関連度主に固定。日付トリアージは GitHub MCP 委譲（issue #41 を見直し）。
