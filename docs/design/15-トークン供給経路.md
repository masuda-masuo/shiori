# 詳細設計: トークン供給経路

## この文書の位置づけ

[09-GitHubApp認証](09-GitHubApp認証.md) は「GitHub App でトークンをどう mint するか」の詳細設計。
本書は **mint したトークンをどの経路で消費者に届けるか**、その方式をどう選ぶかを扱う。
`TokenProvider` の実装が複数あるのはこの経路が複数あるからで、どれを選ぶかは好みではなく
**実行環境から一意に決まる**。

規則自体は shiori 固有ではない。同じキーストアと同じ mcp-token を使う sunaba / dev-infra にも
そのまま効く（末尾「他プロジェクトへの適用」）。

## 前提: 連続稼働するマシンが1台も無い

これが設計を規定する最大の制約で、後から効いてくるので先に置く。

| マシン | 止まり方 |
| --- | --- |
| GCP VM `mcp-host-vm` | `mcp-autostop.timer` がクライアント無通信で**電源断**する（非24h稼働） |
| 自宅 WSL | ホストの Windows が**スリープ**する。WSL の VM ごと凍る |

**「常時動いているホストプロセス」を前提にした設計は、この2台のどちらでも成立しない。**

## 決定変数は2つ

### 規則1: 消費者がコンテナなら、credential を消費者側に運ぶ（shiori#188）

キーストア（D-Bus Secret Service）は **bus オーナー UID しか受け付けない**。コンテナは別 UID
名前空間にいるので、原理的に届かない。したがってコンテナ内プロセスに GitHub を叩かせるなら、
鍵かトークンのどちらかを**コンテナまで運ぶ**しかない。

撤去した `McpTokenProvider`（コンテナ内で mcp-token バイナリを解決して自ら mint する）はこの規則を
無視していた。バイナリの解決は成功する（ただのファイルなので）が mint が失敗し、**警告ログ1行のまま
匿名へ静かにフォールバック**して障害を隠した。

### 規則2: 更新責任は消費者が持つ。壁時計で push する方式はダメ（dev-infra#4）

外部のタイマーが定期的にトークンを発行してファイルに置いていく（push）方式には、消せない欠陥が3つある。

1. **起動直後の窓** — サービスが上がった時点でファイルが古いと、タイマーの初回発火まで期限切れ
   トークンで動く。
2. **タイマーが止まると静かに全滅** — 60分後に全同期が 401 になる。可動部が増えるほど壊れる。
3. **サスペンドで壊れる（これが致命的）** — systemd の `OnUnitActiveSec` は **monotonic clock** 基準で、
   サスペンド中は進まない。一方トークンの寿命は **wall clock** で減る。ホストがスリープすると、
   復帰時点でトークンファイルは**期限切れなのに、タイマーは「まだ5分経っていない」と思っている**。
   復帰後しばらく（最大 = タイマー間隔）同期が 401 になる。**間隔を詰めても消えない。**

前提で述べたとおり連続稼働するマシンが無いので、3 は常に踏む。dev-infra#4 は GCP VM でこれを踏んで
壁時計ポーリング型の token refresh を廃止した。WSL でも同じ窓が開いている（自己修復するので
気づきにくいだけ）。

**したがって: トークンは「消費者が必要になった瞬間に発行する（on-demand pull）」しかない。**

## 現行方式の棚卸し

| 方式 | 秘密鍵の置き場 | 更新責任 | 非連続稼働 | 現在の採用先 |
| --- | --- | --- | --- | --- |
| **A. App 秘密鍵ファイル** | **コンテナ内（PEM）** | 消費者（pull） | ◯ 窓なし | GCP VM |
| **B. token-file 橋渡し** | ホストの keystore | 外部タイマー（**push**） | **✗ 窓あり** | WSL |
| C. コンテナ内 mcp-token mint | keystore（届かない） | — | — | **撤去済み**（旧 `McpTokenProvider`） |
| D. ホストで直接 mcp-token | keystore | 消費者（pull） | ◯ 窓なし | ネイティブ実行 / sunaba |

**A と B は、それぞれ片方の性質を犠牲にしている。**

- **A** は pull なので窓が無い。代わりに**長命の秘密鍵（PEM）がコンテナとディスクに載る**。
  漏れたら App 全体、期限なし。
- **B** は鍵をキーストアに隠したままにできる。代わりに **push なので窓ができる**。しかも更新タイマーが
  load-bearing（止めると60分で全滅）。

どちらかを選べ、という二択に見えるが、そうではない。

## 到達点: on-demand mint socket

**両方を同時に満たせる。** 問題は「ホスト側で mint すること」ではなく「壁時計で置いていくこと」
だった。コンテナが**必要になった瞬間にホストのミント役を呼べる**なら、窓は生まれず、鍵はキーストアから
一歩も出ない。

### 仕組み

ホスト側は systemd の **socket activation**。デーモンは常駐しない。

```ini
# shiori-mint.socket
[Socket]
ListenStream=@SHIORI_DIR@/runtime/mint.sock
Accept=yes
SocketMode=0600

[Install]
WantedBy=sockets.target
```

```ini
# shiori-mint@.service   （接続1本につき1インスタンス）
[Unit]
Description=Mint a short-lived GitHub token (one connection)
# キーストアを提供する unit に依存させる。systemd は接続を保持したまま
# 依存を先に起動するので、起動直後のレースが構造的に消える（後述）。
Requires=mcp-keyring.service
After=mcp-keyring.service

[Service]
Type=oneshot
ExecStart=@SHIORI_DIR@/scripts/mint-token.sh
StandardInput=socket
StandardOutput=socket
```

接続が来た瞬間に systemd が `mcp-token github` を1回実行し、**標準出力がそのまま socket に流れる**。
ホスト側に書くコードは実質ゼロ（ユニット2枚＋数行のラッパ）。

コンテナ側は新しい `TokenSocketProvider`（`GITHUB_TOKEN_SOCKET=/run/shiori/mint.sock`）。
Python 標準ライブラリの `socket`（AF_UNIX）で connect → recv → strip するだけ。キャッシュ方針は
`TokenCommandProvider` と同じ（mint は高価なので55分キャッシュ、期限5分前に再取得）。
**`GITHUB_TOKEN_COMMAND=cat ...` という「ファイルを読むのをコマンドに偽装する」間接も消える**
（`shiori_status` の `token_provider` が `token_command` としか出ず、橋渡し方式かどうか判別できない
という診断上の問題も同時に解消する）。

優先順位は **App > TokenSocket > TokenCommand > PAT > 匿名** の5段になる。

### 得られる性質

| 性質 | 効果 |
| --- | --- |
| **pull（消費者が必要な瞬間に引く）** | 起動直後もスリープ復帰後も**窓が無い**。規則2を満たす |
| **鍵はキーストアから出ない** | コンテナにもディスクにも**長命の秘密が無い**。方式Aの弱点を消す |
| **壁時計タイマーが消える** | `refresh-token.sh` / `shiori-refresh.timer` / `runtime/github-token` を撤去できる。load-bearing な可動部が1つ減る |
| **起動時レースが構造的に解ける** | `Requires=mcp-keyring.service` を書けば、systemd が接続を保持したままキーリングを先に上げる。dev-infra#12 §3-3 の「gnome-keyring がバスに Secret Service を登録し終える前に mcp-token を叩いて落ちる」競合はこれで消える。**`Persistent=true` の catch-up タイマーでは解けない類の問題** |

### セキュリティ境界

- **socket をマウントできる者＝トークンを引ける者**。境界はソケットのパーミッションとマウントの有無に
  なる。コンテナは root で動くので UID では守れない。
- 渡るのは **1時間・特定 installation のトークンのみ**。方式A（PEM を渡す）より漏洩時の被害が小さい
  （App 全体・期限なし → 1時間・スコープ限定）。
- socket は abstract namespace ではなく**ファイルシステム上**に置く（bind mount するため）。

### 未決 / PoC が要る点

- **マウントは rw が要る。** `connect(2)` はソケット inode への**書き込み権限**を要求するので、現行の
  `./runtime:/run/shiori:ro` のままでは繋がらない。ソケット専用ディレクトリを rw で分けるのが素直。
- **WSL の docker で unix socket の bind mount が確実に効くか**（要実測）。
- **rootless docker / user namespace 下の UID マッピングとソケットのパーミッション。**
- **mint の同時実行。** `Accept=yes` は接続ごとに別プロセスなので、`app` と `ingest` が同時に引いても
  デッドロックはしないが、短時間の重複 mint を GitHub 側が許容するか（installation token の発行は
  冪等でなく毎回新規なので、レート上問題ないかを確認）。
- **WSL にはキーストアを提供する専用 unit が無い**（GCP の `mcp-keyring.service` に相当するものが、
  ユーザーセッションの D-Bus）。`Requires=` に何を書くかは環境ごとに変わる。

## 移行段階

| Phase | 内容 | 状態 |
| --- | --- | --- |
| **0** | GCP VM を dev-infra#12 の手順で `use_github_app=true` に収束させる（方式A のまま）。**触らない** | dev-infra 側で進行中 |
| **1** | `McpTokenProvider` / `.bat` / `refresh-token.sh --loop` を撤去し、方式 A / B の2本に整理する。**認証の配線は変えない** | 本 PR |
| **2** | `TokenSocketProvider` + socket unit を実装し、**WSL で実証**する。方式B（token-file 橋渡し）を退役させる | shiori#204 |
| **3** | GCP VM に展開し、**方式A も退役できるか**判断する（PEM を VM から追い出す） | Phase 2 の実証後 |

Phase 1 で `TokenFileProvider`（トークンファイルを一級市民として読む provider）を導入する案も検討したが、
**Phase 2 でトークンファイルそのものが消える**ので、作った端から捨てることになる。導入しない。

## 他プロジェクトへの適用

- **sunaba（GCP VM）** — 消費者はホストの `mcp` UID。現在は sudoers 経由で mcp-token を叩いている
  （`GITHUB_TOKEN_COMMAND="sudo -n -u mcpsecrets DBUS_SESSION_BUS_ADDRESS=... mcp-token github"`）。
  これは既に pull 型なので窓は無い（規則2を満たしている）。socket 化すれば **sudoers の設定自体が
  不要**になり、キーストアへの到達手段が1本に揃う。
- **dev-infra** — `mcp-update.sh` が `/opt/shiori/.env` を再生成するとき、現在は方式A の `GITHUB_APP_*` を
  書く。Phase 3 に進む場合、ここが socket unit の配置に変わる。
