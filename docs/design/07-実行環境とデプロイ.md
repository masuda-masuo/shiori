# 詳細設計: 実行環境とデプロイ

## 目的

ホストを汚さず、再現性のある形で DB と MCP サーバーを動かす。

## 構成: Docker Compose（2 常駐サービス + 1 opt-in）

- `db`: PostgreSQL（pgvector + pgroonga/pg_bigm 入りイメージ）。常駐。
- `app`: MCP サーバー（自作コード）。常駐。バックグラウンドで `SHIORI_SYNC_INTERVAL_SECONDS` によるポーリング差分同期を実行。
- `ingest`（profiles: ["ingest"]）: オンデマンドの使い捨て同期ジョブ。opt-in。
- **分離する理由:** app を再ビルド／再起動しても DB を巻き込まない（索引の再構築回避）、コンテナの 1 プロセス原則（PID1）に沿う、DB は公式系イメージを活用。

## 永続化

- DB のデータディレクトリは **named volume** に置く（コンテナの書き込みレイヤーに置くと再ビルドで消え、埋め込みを作り直す羽目になる）。
- 埋め込みモデルの重みも volume にキャッシュ。
- runner 廃止に伴い runner-state volume は撤去済み。

## 起動

- `docker compose up -d` で db + app が立ち上がる。
- ingest は `docker compose run --rm ingest` で実行。

## ingest（同期）の方針（issue #116 で runner 廃止、polling 一本化）

3 経路で索引を最新に保つ:

1. **SHIORI_SYNC_INTERVAL_SECONDS**（主経路）: serve プロセス内のバックグラウンドポーリング自動同期。推奨 10 秒。差分同期はカーソルベースで短時間。
2. **MCP ツール `ingest`**（オンデマンド）: エージェント／ユーザーが「直近の変更がヒットしない」と感じたとき。
3. **CLI `python -m shiori ingest`**（初回・cron）: 初回構築やスケジュール実行。

複数経路が同時に走った場合は PostgreSQL advisory lock（`pg_try_advisory_lock`）で排他し、後発が `skipped` を返す。索引は壊れない。

認証の方針は詳細設計/09 の決定を踏襲する: `build_token_provider()` の優先順位（App > TokenCommand >
PAT > anonymous）に従い、compose デプロイでは GitHub App 秘密鍵ファイル方式（鍵を
app / ingest サービスに渡す）と token-file 橋渡し方式（ホスト側で mint した短命
トークンをファイル経由で渡し、鍵自体はコンテナに渡さない）のどちらかを使う。実運用（WSL）の
常設稼働は systemd user unit（`shiori.service` / `shiori-refresh.timer`）で行っており、後者の
方式を使っている（詳細は `guides/セットアップ.md`）。方式の選択規則と、
連続稼働しないマシンでの制約は詳細設計/15。serve のバックグラウンドポーリングは
同一プロセス内で動作するため、別途トークン管理は不要。
