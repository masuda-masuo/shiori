# 詳細設計: データストアとスキーマ

## 目的

ベクトル・全文・メタデータを単一の PostgreSQL に統合し、ハイブリッド検索とフィルタを SQL で完結させる。

## 採用技術

- **PostgreSQL**
- **pgvector:** 埋め込みの格納とベクトル類似度検索（コサイン等）。
- **pgroonga:** 日本語対応の全文検索（キーワード）。索引作成時に TokenMecab（形態素解析）を試み、プラグインが無ければ TokenBigram にフォールバックする。
- **構造化列:** メタデータ（`repo`, `path`, `source_type`, `language`, `state`, 日付, 番号 等）。

## 設計の利点

- 1 つの DB でベクトル＋全文＋メタデータを扱える。
- ハイブリッドの融合（例: RRF）と、メタデータのフィルタ（`WHERE` 句）を同一クエリで実行できる。別システム間の同期・結果融合を自前で持たずに済む。

## スキーマ

```sql
CREATE TABLE chunks (
    id BIGSERIAL PRIMARY KEY,
    chunk_key TEXT NOT NULL,
    chunk_index INTEGER NOT NULL DEFAULT 0,
    source_type TEXT NOT NULL CHECK (source_type IN ('doc', 'issue', 'pr_review', 'code')),
    repo TEXT NOT NULL,
    path TEXT,
    issue_no INTEGER,
    comment_id BIGINT,
    language TEXT,
    heading_path TEXT,
    content TEXT NOT NULL,
    embedding vector({dim}),
    state TEXT,
    author TEXT,
    line INTEGER,
    end_line INTEGER,
    commit_sha TEXT,
    prog_lang TEXT,
    symbols TEXT,
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ,
    url TEXT,
    UNIQUE (chunk_key, chunk_index)
);
```

## 索引

### 軽量索引（常時作成）
- `chunks_repo_idx` (btree, repo)
- `chunks_source_type_idx` (btree, source_type)
- `chunks_updated_at_idx` (btree, updated_at)
- `chunks_repo_issue_no_idx` (btree, repo, issue_no)

### 重量索引（HNSW + pgroonga）
- `chunks_embedding_hnsw` — HNSW (cosine)。pgvector の既定パラメータ（m=16, ef_construction=64）。
- `chunks_content_pgroonga` — pgroonga（content）。TokenMecab 優先、フォールバック TokenBigram。
- `chunks_symbols_pgroonga` — pgroonga（symbols）。コード検索の識別子分割用（issue #33）。

### バルク経路での索引管理（issue #72）

初回／rebuild では、重量索引を**データロード後に一括作成**する:
1. `migrate_light()`: テーブル＋軽量索引のみ作成
2. `drop_heavy_indexes()`: 重量索引を DROP（初回は未作成のため no-op）
3. 全データをロード（索引なしのため 1 行ずつの HNSW グラフ構築・形態素索引更新が発生しない）
4. `create_heavy_indexes()`: 全データに対して一括で重量索引を作成

増分経路では、`migrate()` が `migrate_light() + create_heavy_indexes()` を実行し、従来どおり全索引を維持する。

## その他のテーブル

- `sync_state(repo, kind, cursor)`: 差分同期カーソル
- `sync_runs(repo, route, finished_at, docs_updated, issues_indexed, code_indexed)`: 同期実行記録（issue #22）
- `doc_files(repo, path, content_sha, language, kind)`: ファイル単位の content ハッシュ追跡
- `issue_items(repo, issue_no, comment_id, kind, title, author, is_bot, state, path, line, body, url, created_at, updated_at)`: read_issue 用生データ
- `pr_changes(repo, issue_no, head_sha, path, status, additions, deletions, changes, blob_url)`: PR 変更ファイルマップ（issue #54）
