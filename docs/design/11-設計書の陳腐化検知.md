# 詳細設計: 設計書の陳腐化検知

> ドラフト — issue #74 に対応。受け入れ条件が確定したら `docs/design/00` 決定ログに追記する。

## 目的

「設計書とコードが食い違っている」状態を継続的に検知し、人手のレビューに頼らずに
設計書が静かに腐ることを防ぐ。判定基準は**「ドキュメントの最終編集日時」ではなく
「人が整合を確認したコミット」**（`reviewed_at`）に置く。

これにより
- リファクタや整形など設計に影響しない編集での誤検知を抑制できる。
- 「確認した」という acknowledgment を git 上の成果物（フロントマター）として残せる。

## 隣接設計との関係

| 設計書 | 範囲 | 本書との差 |
|---|---|---|
| #22 / #31 / #35（`shiori_status`） | 索引 vs リポジトリの「取り込み鮮度」 | 別軸。索引が新しくても設計書は腐り得る |
| #78（doc↔code 矛盾検出） | 内容的な食い違い（意味軸） | 本書は「コードが動いたか（時間軸）」で、#78 は「何が食い違うか（意味軸）」 |

## 3 つの構成要素

### 1. 設計書フロントマター（紐付けの正本）

設計書自身に「どのコードをカバーするか」と「最後に確認したコミット」を持たせる。
git に乗るため PR レビュー可能、ドキュメントと一緒に移動・削除される。

```yaml
---
shiori:
  covers:
    - src/shiori/github_sync.py
    - src/shiori/ingest.py
  reviewed_at: <commit-sha>   # 最後に「設計書と実装が整合している」と確認したコミット
  reviewed_on: 2026-06-15     # 人が読むための日付（任意）
---
```

**格納先:** `doc_files` テーブルに `covers`(text[]) / `reviewed_at`(text) / `reviewed_on`(date) を追加し、
`ingest` の doc 取り込みパスでフロントマターをパースして格納する。

**代替案と却下理由:**
- 中央マニフェスト（`.shiori/links.yml`）: ドキュメントと別ファイルなので PR レビューが分散し、
  移動・削除への追従が手間。フロントマター正本を採用。
- 索引 DB のみ: git 上の成果物にならず、確認した記録がコードリポジトリに残らない。

### 2. 陳腐化判定 — `reviewed_at` 基準の git ドリフト

```
git log <reviewed_at>..HEAD --oneline -- <covers の各パス>
```

差分コミットが存在すれば「確認後にコード側が動いた」＝要再確認。
コミット列をエビデンスとして設計書名とともに返す。

**履歴取得方式（選択肢）:**

現状のクローンは `clone --depth=1` + `reset --hard origin/HEAD`（二ストアモデル / #57）のため
`reviewed_at..HEAD` の探索に十分な履歴がない可能性がある。

**推奨: `git fetch --shallow-since=<reviewed_on>` による動的深掘り**

- `_git_fetch_ref()` ヘルパ（#81 で導入）を流用し、`reviewed_on` 以降の履歴だけを fetch。
- private/public 一様に動き、GitHub API に委譲するより自己完結する。
- `reviewed_on` が空の場合は `--deepen=N` で一定深さまでフォールバック。

代替: GitHub compare/commits API に委譲。実装は軽いが private で app トークンが必要になるケースがある。

**スコアリング（並べ替え）:**

差分の有無だけでなく、変更量でスコアリングして優先度を示す:

```python
score = changed_lines + changed_files * 10 + distinct_authors
```

感度は設計書ごとに調整可能にする（フロントマターの `sensitivity: high|normal|low`、任意）。

### 3. 「フィックス」メタ情報の打ち直し

整合を確認した時点で設計書の `reviewed_at` と `reviewed_on` を更新する。
この更新自体が **acknowledgment（確認の記録）** になり、次回以降はそのコミット以降の差分だけが評価対象になる。

## ツール設計

### `shiori_stale` ツール（新設）

`shiori_status` への相乗りではなく独立ツールとして設ける（status の責務の肥大化を防ぐ）。

```python
shiori_stale(
    repo: str | None = None,
    top_k: int = 20,          # 上位 N 件を返す
    min_commits: int = 1,     # ドリフトコミット数の閾値
) -> list[StaleEntry]
```

戻り値の各エントリ:

```python
@dataclass
class StaleEntry:
    doc_path: str
    reviewed_at: str          # 確認済みコミット SHA
    reviewed_on: date | None
    covers: list[str]         # カバー対象パス
    drift_commits: list[str]  # reviewed_at 以降の差分コミット（SHA + message）
    score: int                # 変更量スコア
```

### CI チェック（任意）

`covers` 配下のコードを触る PR で、対応設計書の `reviewed_at` が未更新なら warning を出す。
**設計変更トリガー:** 次回のコード変更時に本設計書に `covers` が不足していれば検知する。

## スキーマ変更

`doc_files` テーブルに列を追加:

```sql
ALTER TABLE doc_files
  ADD COLUMN covers       text[],
  ADD COLUMN reviewed_at  text,       -- commit SHA
  ADD COLUMN reviewed_on  date;
```

`chunks` テーブルの変更は不要（フロントマター情報は `doc_files` で管理し、検索には使わない）。

## `covers` パスの追従

ファイルリネームで `covers` が古いパスを指し続けるリスクがある。
初版では**警告として提示する**にとどめ（自動追従は別イシュー）:
- `shiori_stale` 実行時に `covers` 内の存在しないパスを `missing_paths` として返す。

## 受け入れ条件

- [ ] `doc_files` に `covers` / `reviewed_at` / `reviewed_on` 列を追加し、migrate で適用
- [ ] ingest の doc パスでフロントマター（`shiori:` キー）をパースして `doc_files` に格納
- [ ] `git log reviewed_at..HEAD` によるドリフト検出ロジック（履歴取得は動的深掘り方式）
- [ ] `shiori_stale` ツールを MCP サーバーに追加し、スコア降順で一覧を返す
- [ ] `covers` 内の不在パスを `missing_paths` として警告
- [ ] 判定基準が「ドキュメント最終編集」でなく `reviewed_at` であることをテストで担保
  - 例: `reviewed_at` 後にコードだけを変更 → stale。ドキュメントだけ編集 → stale にならない。
- [ ] 既存の `shiori_status` と責務が重ならないことをドキュメントに明記
- [ ] 設計書追加: 本ファイル（`docs/design/11`）。関連して `04`（スキーマ）/ `06`（ツール）に追記

## 非目標

- index 鮮度（索引 vs リポジトリ）の変更（#22 / #31 / #35 の範囲）
- `covers` の自動マッピング（初版は人手の `covers` を正とし、自動提案は別イシュー）
- リネーム検知の自動追従（初版は `missing_paths` 警告のみ）
- 意味的な矛盾検出（→ #78）

## 決定事項

| 決定 | 内容 | 理由 |
|---|---|---|
| フロントマターを正本 | `covers`/`reviewed_at` は設計書 YAML フロントマターに持つ | git に乗り PR レビュー可能、ドキュメントと同一ライフサイクル |
| 独立ツール `shiori_stale` | `shiori_status` への相乗りでなく新設 | status の責務肥大化を防ぐ |
| 履歴を動的深掘り | `git fetch --shallow-since` で必要分だけ取得 | private 一様、自己完結、#81 ヘルパを再利用 |
| 判定基準は `reviewed_at` | ドキュメント最終編集日時を使わない | リファクタ等での誤検知を抑制 |
