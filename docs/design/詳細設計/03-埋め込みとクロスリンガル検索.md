# 詳細設計: 埋め込みとクロスリンガル検索

## 目的

意味検索（semantic search）のための埋め込みを、日英混在・ローカル実行の制約下で設計する。

## モデル選定の方針

- 多言語、できれば**クロスリンガル対応**の埋め込みを選ぶ。
- クロスリンガルが必要な理由: クエリは主に日本語、公開ドキュメントは英語。言語の壁は「クエリとコーパスの間」に残る。日本語クエリで英語ドキュメントを引けることが価値になる。
- 候補: BGE-m3、multilingual-e5(large) など、日英を共通ベクトル空間に寄せるもの。
- 選定は**自分の JA/EN データで実際に検索精度を測って**決める（言語ペアで品質が変わるため）。

## 実行環境

- ローカル実行（非公開データを外部に出さない）。
- モデルの重み（数百 MB 〜）は named volume にキャッシュし、再ビルドで再ダウンロードしない。

## 決定（v1 実装, 2026-06）

- **既定モデルは `intfloat/multilingual-e5-small`（384 次元）。** 理由: クロスリンガル（JA クエリ → EN ドキュメント）対応で、CPU でも取り込み・検索が現実的な速度。BGE-m3 / e5-large は品質候補として残すが、まず軽量モデルで運用し、自分のデータで精度を測ってから差し替える方針（モデル選定の原則どおり）。
- **モデルは `EMBEDDING_MODEL` / `EMBEDDING_DIM` 環境変数で差し替え可能。** 次元が変わるためモデル変更時は `shiori ingest --rebuild` で再索引する。次元不一致は起動時に検出してエラーにする。
- **e5 系のプレフィックス（`query: ` / `passage: `）は埋め込み層で自動付与**（モデル名に `e5` を含む場合）。
- **ベクトルは正規化して格納し、pgvector の HNSW（`vector_cosine_ops`）で索引。** パラメータは pgvector の既定値（m=16, ef_construction=64）。本プロジェクトの規模（数千〜数万チャンク）では調整不要。
- **取り込み時はバッチ埋め込み（batch_size=32）。** 重みのキャッシュ先は `HF_HOME=/models`（named volume）。

## 検討事項 / 未決
