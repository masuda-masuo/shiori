# 詳細設計: データ取り込みと同期

## 目的

docs と issue/PR の 2 系統を、それぞれ適した経路でローカルに取り込み、最新状態を保つ。

## データ源と経路

- **ドキュメント（Markdown）:** `git clone` / `git pull`。リポジトリをローカルに複製し、`.md` を抽出。
- **issue / PR / コメント:** GitHub API（REST/GraphQL）。issue 本文、コメント、PR レビューコメント（ファイル・行に紐づく）を取得。
- **非公開リポジトリ:** トークン（または GitHub App）認証が必要。
- API 利用にはレート制限とページネーションがある。

## 同期戦略

- **docs:** 更新頻度が低いので定期 `pull` で十分。
- **issue/PR:** コメントが日々増えるため、差分同期（`updatedAt` 以降のみ取得）が重要。
- 取り込みは ingest ジョブとして実行（手動 or スケジュール）。

## メタデータ（取り込み時に付与）

`repo`, `path`, `source_type`(doc/issue/pr_review), `language`(ja/en), `state`(open/closed), `author`, `created_at` / `updated_at`, issue/PR 番号, 関連 PR/issue,（doc: 見出しパス）,（pr_review: ファイル・行）

## 決定（v1 実装, 2026-06）

- **同期の起動方式: オンデマンドの ingest。** 当初は `docker compose run --rm app python -m shiori ingest` による CLI 実行のみで、MCP ツールとしての公開は v1 では見送り（同期は長時間ジョブで、ツール呼び出しのタイムアウトと相性が悪いため）としていたが、issue #6 で方針を変更し `shiori_ingest(rebuild?)` として MCP ツール化した。長時間化への対応は差分同期を基本とすることで回避し、CLI / 自動同期 / self-hosted runner など他経路との同時実行は PostgreSQL advisory lock により直列化する（`詳細設計/07`）。CLI（`python -m shiori ingest`）も初回構築や cron 用に引き続き提供する。
- **差分同期の実装:**
  - docs: shallow clone / fetch 後、ファイルごとの content ハッシュ（sha256）を `doc_files` に保持し、差分のあるファイルだけ再チャンク・再埋め込み。削除されたファイルの索引も削除する。
  - issue/PR: REST のリポジトリ横断エンドポイント 3 本（`/issues`・`/issues/comments`・`/pulls/comments`）を `sort=updated&direction=asc&since=` で叩き、最後に処理した `updated_at` を `sync_state` にカーソルとして保存する。
- **ノイズ除去:** bot（`user.type == "Bot"` または login が `[bot]` で終わる）のコメントは原則**索引から除外**する。ただし生データは `issue_items` に `is_bot=true` で保持し、`shiori_read_issue` ではスレッドの一部として表示する（文脈として必要な場合があるため）。環境変数 `SHIORI_INDEX_BOT_LOGINS`（カンマ区切り）で指定した login は bot 判定されても索引対象にする allowlist として機能する（issue #25）。設定値は GitHub App の名称に `[bot]` を付与したログイン名（例: App 名が `my-agent` なら `my-agent[bot]`）。複数指定可。メンテナ回答の優先（重み付け）は v1 では行わない。また、GitHub API から取得したテキスト（title, body, diff_hunk）から、PostgreSQL の text 型に格納できない NUL (0x00) を含む制御文字（0x00-0x1F、ただし改行・タブを除く）を除去する（issue #73）。
- **PR diff: 索引しない。** PR の説明・レビューコメントを索引し、レビューコメントには紐づく `diff_hunk` を文脈として本文末尾に付与する（コード片もキーワード検索に引っかかる）。diff 全体は GitHub の URL から辿る。
- **state は open / closed の 2 値。** merged 判定は PR ごとの追加 API 呼び出しが必要なため v1 では持たない（将来の課題）。
- **allowlist の強制（issue #63）:** `shiori_ingest`（MCP ツール）および CLI 経路（`python -m shiori ingest`）で、明示的に指定された `repo` が `SHIORI_REPOS`（`settings.repos`）に含まれていることを検証し、含まれないものは拒否する。`_do_sync` / `run_ingest` の冒頭（ロック取得前）で照合する。
- **`rebuild=True` の MCP ガード（issue #63）:** `shiori_ingest` の `rebuild=True`（全 TRUNCATE）は MCP ツールからは既定で無効化されており、環境変数 `SHIORI_ALLOW_REBUILD=true` 設定時のみ許可される。CLI 経路（`python -m shiori ingest --rebuild`）はこの制約を受けず常に許可。

### 初回／rebuild のバルク経路最適化（issue #72）

初回（`chunks` 空）または `--rebuild` では、以下の最適化を適用する:

- **重量索引の遅延作成:** `migrate_light()` でテーブル・btree 索引のみ作成し、HNSW・pgroonga(content/symbols) の 3 索引は DROP（または未作成）のままデータロード。全データロード後に `create_heavy_indexes()` で一括作成。逐次構築（1 行ずつ HNSW グラフ更新＋形態素索引更新）を回避し、バルクロード性能を大幅に改善する。
- **埋め込みのファイル横断バッチ化:** `ChunkBuffer` がチャンクを蓄積し、数百件単位で `embed_passages` にまとめて渡す。小バッチ多発によるスループット劣化を削減する。
- **チャンク挿入のバルク化:** `bulk_insert_chunks()` が `executemany` で一括 upsert し、commit 粒度を粗くする。索引なしロードとの併用により fsync 多発も抑制。

増分経路（差分同期）では従来どおり `migrate()` で全索引を維持し、`ChunkBuffer` は使わず `insert_chunk` を直接呼ぶ。挙動は完全に不変。

## 同期の責任分担と推奨構成（public / private）

> 認証構成と「誰が何を同期するか」は繰り返し論点になるため明文化する。本節は `詳細設計/09`（GitHub App 認証）と一体で読む。

### 推奨構成（単一トポロジ: GitHub App + runner）

- GitHub App 秘密鍵は ingest / runner サービスにのみ渡す。常駐 app（MCP サーバー）には渡さない（鍵を MCP サーバーに届かせない。`詳細設計/09`）。
- runner（self-hosted, push / issue / PR イベント駆動。issue #6）が特権 fetch（`git clone` / GitHub API）を行い、DB（索引）とクローンを更新する。
- app は同期済みのローカルデータを read するだけ（トークンレス）。他経路との同時実行は advisory lock で直列化（`詳細設計/07`）。

この構成は public / private のどちらでも同一に機能する。private では必須、public でも構成を揃えるため同じトポロジを推奨する。

### read 経路はトークン不要

`shiori_read_file`（クローン）/ `shiori_read_issue`・検索（索引）は同期済みデータを読むだけなので、app がトークンレスでも、runner が同期済みであれば private の内容も返せる。これが「app にコンテンツをライブ取得させない」設計の根拠であり、PR diff/全文をポインタ層に留める方針（上記「PR diff: 索引しない」および issue #54）とも一致する。

### スコープ外（複雑化を避けるため考慮しない）

- **長期トークン（PAT）運用:** 非推奨。お試し／ローカル検証以外では使わない（失効・権限・セキュリティの面で App に劣る）。
- **runner なしの private 同期:** 非対応。app に直接 fetch させる構成は鍵を app に渡すことになり、上記のセキュリティモデルを壊すため考慮しない。
- **匿名同期:** public のお試しのみ（未認証 60 req/h 制限）。

### 認証の優先順位（実装上の挙動）

`build_token_provider`: GitHub App > PAT > 匿名。推奨は上記のとおり App。
