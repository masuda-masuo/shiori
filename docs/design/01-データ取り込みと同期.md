# 詳細設計: データ取り込みと同期

## 目的

docs と issue/PR の 2 系統を、それぞれ適した経路でローカルに取り込み、最新状態を保つ。

## データ源と経路

- **ドキュメント（Markdown）:** `git clone` / `git pull`。リポジトリをローカルに複製し、`.md` を抽出。
- **issue / PR / コメント:** GitHub API（REST/GraphQL）。issue 本文、コメント、PR レビューコメント（ファイル・行に紐づく）を取得。
- **非公開リポジトリ:** トークン（または GitHub App）認証が必要。
- API 利用にはレート制限とページネーションがある。

## 同期戦略

- **docs:** 更新頻度が低いので定期 `pull` で十分。
- **issue/PR:** コメントが日々増えるため、差分同期（`updatedAt` 以降のみ取得）が重要。
- 取り込みは ingest ジョブとして実行（手動 or スケジュール）。

## メタデータ（取り込み時に付与）

`repo`, `path`, `source_type`(doc/issue/pr_review), `language`(ja/en), `state`(open/closed), `author`, `created_at` / `updated_at`, issue/PR 番号, 関連 PR/issue,（doc: 見出しパス）,（pr_review: ファイル・行）

## 決定（v1 実装, 2026-06）

- **同期の起動方式: オンデマンドの ingest。** 当初は `docker compose run --rm app python -m shiori ingest` による CLI 実行のみで、MCP ツールとしての公開は v1 では見送り（同期は長時間ジョブで、ツール呼び出しのタイムアウトと相性が悪いため）としていたが、issue #6 で方針を変更し `shiori_ingest(rebuild?)` として MCP ツール化した。長時間化への対応は差分同期を基本とすることで回避し、CLI / 自動同期 / self-hosted runner など他経路との同時実行は PostgreSQL advisory lock により直列化する（`詳細設計/07`）。CLI（`python -m shiori ingest`）も初回構築や cron 用に引き続き提供する。
- **差分同期の実装:**
  - docs: shallow clone / fetch 後、ファイルごとの content ハッシュ（sha256）を `doc_files` に保持し、差分のあるファイルだけ再チャンク・再埋め込み。削除されたファイルの索引も削除する。
  - issue/PR: REST のリポジトリ横断エンドポイント 3 本（`/issues`・`/issues/comments`・`/pulls/comments`）を `sort=updated&direction=asc&since=` で叩き、最後に処理した `updated_at` を `sync_state` にカーソルとして保存する。
- **ノイズ除去:** bot（`user.type == "Bot"` または login が `[bot]` で終わる）のコメントは**索引から除外**する。ただし生データは `issue_items` に `is_bot=true` で保持し、`shiori_read_issue` ではスレッドの一部として表示する（文脈として必要な場合があるため）。メンテナ回答の優先（重み付け）は v1 では行わない。
- **PR diff: 索引しない。** PR の説明・レビューコメントを索引し、レビューコメントには紐づく `diff_hunk` を文脈として本文末尾に付与する（コード片もキーワード検索に引っかかる）。diff 全体は GitHub の URL から辿る。
- **state は open / closed の 2 値。** merged 判定は PR ごとの追加 API 呼び出しが必要なため v1 では持たない（将来の課題）。
