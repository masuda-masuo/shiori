# 詳細設計: プロダクト定義とユースケース

> 背景: shiori は当初 RAG（検索拡張生成）の基盤として構想された。しかし機能追加を重ねる中で、検索対象は docs から issue/PR の議論・ソースコードへ広がり、検索以外のツール（読む・構造を見る・関係をたどる）が増え、実態は「プロジェクトナレッジへのアクセス層」に変わっている。定義が構想時のまま曖昧だと、ユーザー（人間・エージェント双方）がどの場面で shiori を使うべきか判断できない。本書は現時点のプロダクト定義を確定し、ツール群の位置づけとユースケースを定義する。

## 1. 一文定義

**shiori は、GitHub リポジトリに散在するプロジェクトナレッジ — ドキュメント・ソースコード・issue/PR の議論 — を、AI エージェントが低トークンで検索・参照するためのローカル MCP サーバーである。**

「プロジェクトナレッジ」とは、そのプロジェクトについての問いに答えるために必要な情報の総体を指し、次の 3 種で構成される:

| ナレッジの種類 | 実体 | 答える問い |
|---|---|---|
| 確定した現在（What / How） | main 上のドキュメント・ソースコード | 何をするものか・どう動くか・どう使うか |
| 経緯と判断（Why） | issue / PR の本文・コメント・レビュー | なぜこうなっているか・却下案・既知バグ・回避策 |
| 進行中の変更（What's changing） | open PR の変更ファイル・diff・レビュー | いま何が変わろうとしているか |

## 2. なぜ「RAG」ではないのか

RAG は「検索結果をコンテキストに注入して LLM が回答を**生成する**」パイプライン全体を指す。shiori はこのうち検索（Retrieval）部分だけを担い、**回答を生成しない**。

- 生成と判断の主体はエージェント側にある。shiori は素材（ポインタ＋スニペット＋座標）を返すだけで、要約も回答合成もしない（issue スレッドを生のまま索引する決定も同じ思想 — `詳細設計/02`）。
- RAG が前提とする「検索結果を自動でコンテキストに詰める」動きもしない。shiori は検索でポインタを返し、エージェントが**必要だと判断したときだけ** read 系ツールで取得する（pointer-then-fetch — `詳細設計/00` 設計原則）。
- 検索だけでなく、構造閲覧（`list_tree`）・相互参照（`issue_links`）・PR 変更追跡（`pr_changes` / `pr_diff`）など、検索の枠に収まらないナレッジナビゲーションを提供する。

したがって shiori の正しい呼び名は「RAG サーバー」ではなく「**プロジェクトナレッジ検索 MCP**」（エージェントから見ればナレッジアクセス層）である。

## 3. スコープ — 何であって、何でないか

### shiori である（やること）

- **確定情報の一次窓口**: main 上の docs / code を検索し、必要な断片だけ取得させる
- **「なぜ」への到達手段**: issue / PR に埋もれた経緯・判断・暗黙知を検索可能にする
- **低トークン**: 全文をコンテキストに流さない。ポインタ → 必要分 fetch の 2 段構え
- **ローカル・プライベート**: 索引・埋め込み・検索はすべてローカルで完結し、データを外部に出さない
- **クロスリンガル**: 日本語で尋ねて英語ドキュメントを引く（逆も）

### shiori でない（非目標と委譲先）

| 非目標 | 理由 | 委譲先 |
|---|---|---|
| 回答生成（RAG の G） | 判断・生成はエージェントの責務 | エージェント / LLM |
| GitHub の再発明 | 未確定コンテンツの全文保持・日付トリアージ・issue/PR への書き込みは既存機能の重複 | GitHub MCP |
| コード実行・検証 | 検索と実行は別の関心事 | code-sandbox-mcp（`詳細設計/12` でクローン連携） |
| リポジトリへの書き込み | shiori は読み取り専用（索引の同期を除く） | GitHub MCP / git |
| リアルタイム性の保証 | 索引は同期時点のスナップショット。鮮度は `shiori_status` で自己申告する | 最新が必要なら同期 or GitHub MCP |

## 4. ツールカタログ — 4 層モデル

12 ツールを「ユーザーの問い」で 4 層に分類する。新しいツールを追加するときは、どの層に属するかをまず決めること（どの層にも収まらないツールはスコープ外の疑いがある）。

| 層 | ユーザーの問い | ツール |
|---|---|---|
| ① 検索（入口） | どこに書いてある？ | `shiori_search` / `shiori_keyword_search` / `shiori_grep` |
| ② 閲覧 | 何と書いてある？ | `shiori_read_file` / `shiori_read_issue` / `shiori_read_pr_file` / `shiori_list_tree` |
| ③ 関係・変更 | 何とつながっている？何が変わる？ | `shiori_issue_links` / `shiori_pr_changes` / `shiori_pr_diff` / `shiori_pr_review_comments` |
| ④ 運用 | 索引は新しいか？ | `shiori_status` |

### ① 検索層 — 3 ツールの使い分け（検索ファネル）

粗い問いから細かい問いへ絞り込むファネルとして設計されている:

1. **`shiori_search`** — 統合入口。意味＋キーワードのハイブリッド（RRF 融合）。概念・言い換え・クロスリンガルな問いに強い。迷ったらまずこれ。
2. **`shiori_keyword_search`** — 厳密一致。関数名・API 名・エラーコード・設定キーなど識別子で引くときに使う。
3. **`shiori_grep`** — Stage-2。①②でファイルを特定した後、クローンを ripgrep して行レベルの位置を確定する。

検索層の結果は常に**ポインタ**（パス／見出しパス／issue 番号＋スニペット＋URL）であり、全文は返らない。

主要フィルタ: `source_type`（doc / issue / pr_review / code）、`kind`（issue / pr）、`repo`（`"*"` で横断）、`path_prefix`、`prog_lang`、`state`、`updated_after`。

### ② 閲覧層 — 必要分だけ読む

- **`shiori_read_file`** — クローン（main 固定）の実ファイルを読む。`start_line` / `end_line` で範囲指定。
- **`shiori_read_issue`** — issue/PR スレッド全体を時系列で取得（本文＋コメント＋レビュー）。`numbers` で最大 50 件の一括取得。
- **`shiori_read_pr_file`** — PR head 時点のファイルを git 経由で透過取得（ワーキングツリー非破壊 — issue #81）。
- **`shiori_list_tree`** — リポジトリ構造の閲覧。`source_type='doc'/'code'`・`extension` で絞り込み。

### ③ 関係・変更層 — ナレッジをたどる

- **`shiori_issue_links`** — issue/PR の相互参照（inbound/outbound）を種別付き（closes / duplicate / refs / mention）で返す（issue #97）。重複チェック・epic 構築・回帰追跡に使う。
- **`shiori_pr_changes`** — PR の変更ファイルマップ（head_sha / path / status / 増減 / blob_url）。レビューや影響調査の起点。
- **`shiori_pr_diff`** — PR の unified diff を git で計算して返す（issue #96）。`path` 指定で単一ファイルに絞れる。
- **`shiori_pr_review_comments`** — PR のレビューコメント一覧（パス・行番号付き）。他レビュアーの指摘の把握に使う。

### ④ 運用層

- **`shiori_status`** — リポジトリごとの最終同期時刻・チャンク内訳・カーソル・警告（`詳細設計/06`）。索引が古い場合は CLI `python -m shiori ingest` または自動同期で更新する（MCP ツールとしての ingest は廃止済み）。

## 5. ユースケース

エージェント（および人間ユーザー）が shiori を使う典型シナリオ。各ユースケースは「問い → ツールフロー → 得られるもの」で記述する。

### UC-1: 仕様・使い方の確認（オンボーディング）

> 「この機能の仕様はどこに書いてある？」「セットアップ手順は？」

```
shiori_search(query, source_type="doc")
  → 該当ドキュメントのポインタ＋スニペット
  → shiori_read_file(path, start_line, end_line)  # 必要な節だけ読む
```

新規参加者・新規エージェントが、リポジトリ全体を読まずに確定仕様へ最短到達する。クロスリンガル対応により日本語の問いで英語 docs も引ける。

### UC-2: 設計判断の経緯調査（Why の発掘）

> 「なぜ B 案ではなく A 案を採用したのか？」「この制約はどこで決まった？」

```
shiori_search(query, kind="issue")  または kind="pr"
  → 議論スレッドのポインタ
  → shiori_read_issue(number)              # スレッド全体を時系列で読む
  → shiori_issue_links(number)             # 関連 issue / 後続 PR をたどる
```

docs に載らない暗黙知（却下案・トレードオフ・当時の制約）に到達する。設計変更の提案前に「過去に検討済みか」を確かめる用途が典型。

### UC-3: 実装箇所の特定（コードリーディング）

> 「この処理はどこで実装されている？」「この関数はどこから呼ばれる？」

```
shiori_keyword_search(識別子, source_type="code")   # 関数名・クラス名で引く
  → 候補ファイルのポインタ
  → shiori_grep(pattern, path)                      # 行レベルで位置を確定
  → shiori_read_file(path, start_line, end_line)    # 該当範囲だけ読む
```

概念的な問い（「認証まわりはどこ？」）は `shiori_search(source_type="code")` から入る。`shiori_list_tree(source_type="code", extension=".py")` で構造を掴んでから絞る経路もある。

### UC-4: PR レビュー支援

> 「この PR は何をどう変えるのか？」「他のレビュアーは何を指摘している？」

```
shiori_pr_changes(number)            # 変更ファイルマップで全体像
  → shiori_pr_diff(number, path?)    # 差分の中身
  → shiori_read_pr_file(number, path)  # 変更後ファイルの全体文脈
  → shiori_pr_review_comments(number)  # 既存レビューの把握
  → shiori_read_issue(number)          # 議論の経緯
```

さらに `shiori_search` で変更対象に関する設計ドキュメントを引き、「設計と実装の整合」をレビュー観点に加えられる。

### UC-5: バグ・エラー調査

> 「このエラーは既知か？回避策は？」「過去に同じ障害があったか？」

```
shiori_keyword_search(エラーコード・メッセージ)   # 厳密一致で既知 issue を探す
  → shiori_read_issue(number)                     # 原因と回避策を読む
  → shiori_issue_links(number)                    # duplicate / closes で解決 PR へ
  → shiori_pr_changes(解決PR番号)                 # 修正内容の確認
```

「issue（症状）→ 修正 PR → 変更ファイル」の連鎖をたどることで、再発時の調査起点が得られる。

### UC-6: ドキュメントと実装の突き合わせ（陳腐化チェック）

> 「この設計書は実装と一致しているか？」

```
shiori_read_file(設計書パス)                       # 設計上の主張を読む
  → shiori_keyword_search(識別子, source_type="code")  # 実装側を検索
  → shiori_grep(pattern) → shiori_read_file(実装パス, 範囲)
```

`詳細設計/11`（設計書の陳腐化検知）の手動版。設計書更新 PR の作成自体は GitHub MCP に委譲する。

### UC-7: 複数リポジトリ横断調査

> 「この規約はどのリポジトリで使われている？」

```
shiori_search(query, repo="*")   / shiori_grep(pattern, repo="*")
  → 各マッチの repo フィールドで所在を識別
```

`SHIORI_REPOS` に登録された全リポジトリを一括検索する。組織内の複数プロジェクトに知識が分散しているケースの入口。

### UC-8: 索引の健全性確認（運用）

> 「検索結果が古い気がする」「同期は動いているか？」

```
shiori_status()
  → last_synced_at / age_seconds / warnings を確認
  → 古ければ CLI: python -m shiori ingest（または自動同期を待つ）
```

### アンチユースケース（shiori を使わない場面）

| やりたいこと | 使うべきもの |
|---|---|
| issue / PR の作成・コメント投稿 | GitHub MCP |
| 索引にない最新情報（同期後の変更）の取得 | 同期してから shiori、または GitHub MCP |
| CI 状態・リリース・ブランチ操作 | GitHub MCP |
| コードの実行・テスト | code-sandbox-mcp（shiori のクローンをコピーして高速起動 — `詳細設計/12`） |
| 「最近クローズされた issue」等の日付トリアージ | GitHub MCP（`詳細設計/00` 決定ログ） |

## 6. 決定事項

- プロダクト定義を「RAG」から「**プロジェクトナレッジ検索 MCP**」に改める。RAG の G（生成）は担わず、Retrieval とナレッジナビゲーションに徹する。
- ツールは 4 層モデル（検索／閲覧／関係・変更／運用）で分類する。新ツール追加時は所属層をまず決め、本書のカタログを更新する。どの層にも収まらない提案はスコープ外の疑いとして `詳細設計/00` の非目標と照合する。
- README・MCP サーバーの `instructions`・AGENTS.md のツール一覧は、本書のカタログ（12 ツール）と同期させる。

## 7. 検討事項 / 未決

- ユースケースごとの検索精度計測（UC をそのまま評価シナリオに転用できる — `詳細設計/03` の精度計測と連動）
- 層③（関係・変更）の拡張候補: コード側の参照関係（呼び出しグラフ）は現状スコープ外。必要になった時点で非目標との整合を再検討する。
