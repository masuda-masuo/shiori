# 詳細設計: ソースコード索引

> **ステータス: 未実装（設計のみ / draft）。** ディスカッション（2026-06-12〜13）の整理、実装着手前のレビュー用。
> 本書で参照する `split_code` / `sync_code`、`chunks` の新カラム、`config` の `SHIORI_CODE_*` はいずれも未実装。

## 目的 / 背景

shiori は現在 Markdown（doc）と issue / pr_review のみを索引する。実運用で
「設計ドキュメントとソースコードの突き合わせ」を LLM にやらせたところ、コードは
shiori から発見できず、別途 GitHub MCP 等での取得が必要だった。

実態の整理:

- `sync_docs` はリポジトリ全体をクローン済みで、`shiori_read_file` は任意ファイルを返せる。
  欠けていたのは**アクセスではなく発見性**（`shiori_list_tree` と検索が MD 限定）。
- 主たる利用者は、アシスタント / ホワイトボード UI（ドラフト、採番待ち）が想定する
  **チェックアウトを持たないローカル LLM（14B〜32B クラス）**。pointer-then-fetch の
  ナビゲーション能力が高くない前提で、検索側が案内する必要がある。
- 一方、実装レーン（OpenCode 等のコーディングエージェント）は手元にコードがあり
  grep できるため、本件の主対象ではない。

## 決定事項

1. **`source_type='code'` を追加し、ソースコードを索引する。lint / 静的解析の
   finding は索引しない（見送り）。**
   finding は「そのコミット時点の派生事実」で揮発性が最も高く、索引は
   「古いかもしれないキャッシュ」にしかならない。耐久性のある部分
   （dismissed / wontfix の判断経緯）は PR コメントとして索引済み。
   必要になったら code scanning API を直接叩く薄いツール（`shiori_list_alerts(path?)`）を
   足す方が常に新鮮で安い。完了検証の類もライブな証拠（テスト実行・CI 結果）を
   使うべきで、索引済み finding を根拠にしない。
2. **チャンクは「地図型」: シグネチャ＋docstring を内容とし、本文フルは収載しない。**
   - tree-sitter（`tree_sitter_language_pack`）で関数 / メソッド / クラス単位に分割。
     親スコープを `heading_path` に積む（`module.py > class Foo > def bar`。
     `02` の見出しスタックと同型）。チャンク本文の先頭にも同プレフィックスを付与。
   - content = シンボルパス＋シグネチャ＋docstring。自然言語に近いため既存の
     e5（`03`）でも埋まり、クロスリンガル（日本語の問い→英語コード位置）の橋になる。
   - `start_line` / `end_line` を保持し、本文は `shiori_read_file(path, start, end)` へ誘導する
     （ポインタ＋スニペット、全文は read、という既存思想と同型）。
   - 本文フル埋め込みは見送り。根拠: (a) multilingual-e5 はコード本文の埋め込み品質が
     低い（コード特化モデルは日本語に弱く、クロスリンガル方針 `03` と衝突）、
     (b) コーパスが一桁膨れ、ディストラクタに弱いローカル LLM にはノイズ増として
     跳ね返る、(c) 小さいコンテキスト予算（8K〜32K）には短いポインタが適する。
     実機テスト（後述 step 5）で不足が実証されたら opt-in で再検討。
3. **キーワード検索をコード対応にする（`symbols` カラム）。**
   実務のコード RAG はキーワード優先（Zoekt / Cody の回帰、Aider、agentic grep）であり、
   クエリの大半は関数名・型名・エラーメッセージの厳密一致。pgroonga の
   TokenMecab / TokenBigram は `parse_config` / `parseConfig` を分割しないため、
   チャンク生成時（AST walk と同時）に snake / camel 境界で識別子を分割した文字列を
   `symbols` カラムに格納し pgroonga 索引を張る。`keyword_search` の候補クエリを
   `content &@~ %s OR symbols &@~ %s` に拡張する（分割済みスペース区切りのため
   トークナイザは既定で足りる）。`05` の RRF 融合はそのまま（候補ソースが増えるだけ）。
4. **`language`（ja/en）にプログラミング言語を混ぜず、`prog_lang` を別カラムで持つ。**
   `language` フィルタの意味の二重化を避ける。code チャンクは `language=NULL`。
   fs ソース（`08`）と併用時のフィルタプリセットでも曖昧さを残さない。
5. **code ファイルの sha 追跡は `doc_files` に `kind` 列を追加して相乗りする
   （`code_files` 新設はしない）。**
   `08` が fs ソースで `doc_files` を `repo='fs:{name}'` のまま流用する方針と揃え、
   テーブルを増やさない。`kind TEXT NOT NULL DEFAULT 'doc'` とし既存行は無変更。
   `shiori_list_tree` は `source_type` パラメータ（`doc` / `code`）で kind を区別して返す
   （issue #43）。rebuild の TRUNCATE 対象も現行 4 テーブルのまま増えない。
   これにより引用凍結（ホワイトボード UI ドラフト）が code を指せるようになり、
   「決定事項が引用したコードが変わったら要レビューを付ける」＝設計と実装の乖離検知が、
   既存ドリフト機構の自然な拡張として成立する。v1 は sha 不一致の「変わった」バッジ
   止まりとし、行番号の再アンカリングはやらない。
6. **`shiori_list_tree` 拡張は先行して単独リリースする（step 0）。**
   クローン全体を walk（`.git`・除外 glob 適用）して code ファイルも返し、
   ツール docstring と FastMCP instructions に「read_file はコードも読める」を明記する。
   索引・スキーマ無変更の数十行で、本体工事中のつなぎとして即価値が出る。
   step 0 には `source_type` と `extension` フィルタも含める（issue #43）。
7. **対象ファイルは allowlist ＋除外 glob で制御する。**
   `SHIORI_INDEX_CODE`（マスタスイッチ、既定 off）/ `SHIORI_CODE_EXTENSIONS` /
   `SHIORI_CODE_EXCLUDE_GLOBS` を config に追加。node_modules / dist / .venv /
   生成物は必ず除外（量と質の両面）。tree-sitter 非対応の拡張子は
   `_split_long_text` フォールバックで取りこぼしゼロにする。
8. **同期・鮮度の既存機構（`#6` / `#22`）にそのまま乗せる。**
   - `sync_code` は `sync_docs` / `sync_issues` と同じ `_do_sync` / `run_ingest` の
     ループ内で実行し、advisory lock の排他に含める。
   - self-hosted runner の push イベント駆動（issue #6）により、**コード索引の鮮度は
     push のたびに自動で保たれる**。差分は sha デルタなので変更ファイルのみ再埋め込み。
     逆に言えば push ごとの ingest コストが増えるため、決定 2（地図型）と決定 7
     （除外 glob）がコスト抑制を兼ねる。
   - `sync_runs`（issue #22）に `code_indexed INTEGER` を追加し、`shiori_status` で
     code の同期件数も照会できるようにする。

## スキーマ変更（`04` への追記）

| 変更 | 内容 |
|---|---|
| `chunks.source_type` | CHECK 制約に `'code'` を追加 |
| `chunks.end_line` | INTEGER 追加（code は範囲、既存 source は NULL のまま） |
| `chunks.commit_sha` | TEXT 追加（鮮度・permalink 用） |
| `chunks.prog_lang` | TEXT 追加（決定 4） |
| `chunks.symbols` | TEXT 追加＋pgroonga 索引（決定 3） |
| `doc_files.kind` | TEXT NOT NULL DEFAULT 'doc' 追加（決定 5。'doc' \| 'code'） |
| `sync_runs.code_indexed` | INTEGER 追加（決定 8） |

`migrate()` は `CREATE TABLE IF NOT EXISTS` のみのため、既存 DB には
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` と CHECK 制約の drop→add を冪等に追記する。
rebuild の **TRUNCATE は 2 箇所（`mcp_server._do_sync` / `ingest.run_ingest`）**にあるが、
決定 5 によりテーブルは増えないため対象は現行どおり
（`sync_runs` は鮮度記録のため従来から TRUNCATE 対象外。これも踏襲）。

4. 検索配線: `symbols` の OR 検索、`prog_lang` フィルタ
   （`_filter_sql` / `_make_filters` / 両ツールのシグネチャ）、
   両 search ツールの docstring と FastMCP instructions の source_type 説明を更新
5. **実機テスト**: ローカル LLM に実際の設計↔コード比較タスクを実施。
   「ファイルに辿り着けるか」「該当箇所を見つけられるか」を観察し、
   本文フル索引へ進むかをここで判断する（先に賭けない）。

## 関連設計との連動

- **アシスタント / ホワイトボード UI（ドラフト、採番待ち）**: チェックアウトなしの
  ローカル LLM が本件の主受益者。検索側をコード対応にするほど LLM 選定
  （ツール呼び出し精度）のハードルが下がる。引用凍結のロケータに code 対応
  （path＋行範囲＋sha）を足すのは**フロントエンド側バックエンドの作業**であり、
  shiori 改修は本書の範囲で閉じる。同ドラフトの「shiori は無改修で使う」前提に対し、
  本件は read 側の索引拡張（`08` fs ソースと同列の追加改修）として位置づける。
- **`08` fs ソース（未実装）**: 決定 5 で `doc_files.kind` を共有する。fs ソース配下の
  コード索引（ローカル作業ディレクトリの code 対応）は本書のスコープ外 → 検討事項。

## 検討事項 / 未決

- **本文フル索引**: step 5 の結果待ち。導入する場合はコード特化 embedding
  （jina-code 系等）の併用を検討するが、日本語クエリとの相性（`03` のクロスリンガル
  方針と衝突）、および `chunks.embedding` が単一次元のためモデル併用には
  別カラム / 別テーブルが必要になる点がトレードオフ。
- **リランカー**（`05` の未決を引き継ぐ）: top-k 精度の向上はディストラクタに弱い
  ローカル LLM ほど効く。コード検索限定で載せる案を含め、step 5 の後の候補。
- fs ソース（`08`）配下へのコード索引適用（`08` 実装後に判断）。
- `sync_state` の code カーソル: docs と同じ HEAD sha を共有するか、
  walk 自体を `sync_docs` に畳むか（実装時に決定）。
- ドリフト検出の行番号再アンカリング（v2 候補。v1 は sha バッジのみ）。
- finding 用の薄いライブツール `shiori_list_alerts(path?)` の要否（必要になってから）。
- コスト観測: コードは docs より量が出るため、ingest 時間とチャンク数を
  source_type 別に計測してから本文フル索引の判断材料にする。runner（issue #6）の
  push ごとの埋め込み負荷もここで観測する。
